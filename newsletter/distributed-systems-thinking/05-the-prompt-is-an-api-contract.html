The Expensive Answers · Issue 5

The prompt is an API contract

2 October 2026·4 min read·Avishek Nag

There is one interface in a modern system unlike every other. On one end, your code: deterministic, typed, tested. On the other, a language model: it reads English, fills in whatever you leave open, and does not guarantee the same answer twice. The call between them is usually treated as craft, prompt magic, a dark art with folklore instead of discipline.

I want to argue the opposite. The prompt is an interface artifact. Every part of it maps to a contract concept you already maintain, and the mapping is not a metaphor. It is a working discipline, and teams that adopt it stop experiencing model behaviour as weather.

The clause most prompts are missing

Walk the mapping. The system instructions are the interface specification. “Answer only from the provided passages; cite every claim; if the passages do not contain the answer, say so” is a set of preconditions and postconditions, and that last clause is the one most prompts are missing: the defined failure mode, the 404 of the prompt, the specified behaviour for the case where success is impossible. An interface without a failure mode is not underspecified at the edges. It is unspecified exactly where it matters most, and the model will improvise there. Improvisation at the failure boundary has a domain name: hallucination.

This reframes the phenomenon usefully. Ambiguity in a prompt is under-specification in a contract, and a model meeting one does not misbehave. It obeys. It fills the gap the way it fills every gap, from its training distribution, with the most typical completion of the world’s text. The model never breaks your contract; it honours clauses you did not know you had written, supplied by the median of the internet. Read failures this way and they stop being mysteries and become diffs: find the clause you left open, and close it.

The rest of the prompt maps just as cleanly. Few-shot examples are contract test cases: each one asserts a behaviour the caller relies on, so choose them like regression tests, pinning what would hurt most if it drifted, not what demos best. Output format rules are the response schema, and the structured-output modes now offered by every serious API are schema enforcement, the difference between requesting JSON politely and validating it at the boundary; if your code parses the model’s output, enforce, do not request. The model name and version are the dependency declaration, and an unpinned model is an unpinned dependency in production, a sentence that needs no elaboration if you have lived through one. Temperature and token limits are the variance and cost clauses: how much surprise, and how much spend, the caller will accept.

Your prompts deserve code review

And the prompt’s own version number is the piece most teams are missing entirely. A prompt change is an interface change, entitled to the full ritual: a diff someone reviews, a version that increments, a changelog line that says why, a test run before it ships. If your prompts live in a wiki, edited in place, unreviewed and unversioned, then your system’s most sensitive interface has less change control than your CSS.

The day you did nothing

The discipline pays off hardest on the day you did nothing. The vendor upgrades the model; not a word of your prompt changes, and every probability behind its interpretation does. Treated as craft, this is a mystery that arrives like weather. Treated as a contract, it is a dependency upgrade, the most routine event in software, with the most routine response: re-run the contract tests, read the behavioural diff, and decide whether to ship or to pin. The teams that struggle with model upgrades are, almost always, the teams with no contract tests to re-run.

One habit to start this week, if you take nothing else: put your prompts in version control, next to the code that depends on them, and require the same review for a prompt change as for an API change. Everything else, the golden question sets, the automated evaluation, the release tuple that versions model, prompts, index, and evals together, grows naturally from that one habit, and I will get to the machinery in later pieces.

The strangest interface in your system turns out to be the discipline’s best student: specification, tests, schema, dependency pin, variance clause, version. Written that way, a prompt is reviewable. And what is reviewable can be owned.

A question worth putting to your own team, because the answer is usually illuminating: who reviews prompt changes today, and what would have to be true for the answer to be “the same people who review API changes”? Next issue returns to the pipeline behind these interfaces, with a story: seventy-four documents vanish from a healthy system while every dashboard stays green, and the question that follows turns out to be the whole of delivery semantics: what does a duplicate cost?
